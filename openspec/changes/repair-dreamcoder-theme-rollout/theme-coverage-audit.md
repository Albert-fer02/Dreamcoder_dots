# Theme Coverage Audit: Canonical Dreamcoder Light/Dark Rollout

## Executive decision

Consolidate the four related SDDs under `repair-dreamcoder-theme-rollout`, but preserve their ownership boundaries: the Ghostty repair remains a narrow remediation, Herdr remains runtime-contract gated, and the design-system change remains the validation foundation. The canonical rollout is the token-driven Python engine plus generated repository snippets and controlled ML4W/Gentleman apply hooks. No target should own independent color literals.

This audit is read-only. Existing dirty-worktree changes are evidence only and are not interpreted as authored by this change.

## Canonical source of truth

| Layer                         | Canonical ownership                                           | Boundary                                            |
| ----------------------------- | ------------------------------------------------------------- | --------------------------------------------------- |
| Palette values and guardrails | `DreamcoderThemes/dreamcoder/tokens.json`                     | Only place for color decisions                      |
| Schema                        | `DreamcoderThemes/dreamcoder/tokens.schema.json`              | Token shape and mode validity                       |
| Static generated tokens       | `src/dreamcoder_theme/palette_tokens.py`                      | Regenerated by `scripts/generate-palette-tokens.py` |
| Runtime loading/contrast      | `src/dreamcoder_theme/palette.py`                             | WCAG/APCA guards and variant loading                |
| Rendering                     | `src/dreamcoder_theme/renderers.py` and leaf `renderers_*.py` | Pure deterministic target serialization             |
| Orchestration                 | `src/dreamcoder_theme/sync.py`                                | Active writes and repository variants               |
| File writes                   | `src/dreamcoder_theme/writers.py`                             | `write_if_changed` and target-specific safe updates |
| Mode selection/apply          | `scripts/apply-theme-mode.sh` and `scripts/theme-auto.sh`     | Explicit and scheduled Light/Dark convergence       |
| Health gate                   | `scripts/verify-theme-health.py` and focused pytest           | Blocking evidence, not visual identity              |

`dusk` exists in the token/design-system contract, but runtime activation currently accepts only `light` and `dark`; dusk must remain an in-memory/validation mode unless a separate product decision expands activation.

## ML4W installation and apply boundary

Dreamcoder is an overlay on Gentleman Dots and ML4W, not a replacement. ML4W remains owner of layout, behavior, wallpaper, Matugen lifecycle, Hyprland/Waybar/Rofi structure, and launch scripts. Dreamcoder owns color-bearing generated snippets and must be imported after ML4W/Gentleman defaults.

Installation currently Stows Shell, Kitty, Ghostty, Fastfetch, Warp, Bat, and Systemd. It applies ML4W hooks and enables the theme timer, but does not include Herdr. Therefore Herdr is currently an integration gap, not an installed first-class target. Any Herdr provisioning must be separately classified, conflict-safe, and must not silently adopt external files.

`apply-theme-mode.sh` is the fan-out boundary: it validates mode, applies system mode, optionally invokes Matugen, flips mode symlinks before Python sync, invokes the generator, reloads selected consumers, propagates Tmux values, then invokes Herdr and repairs remaining active links. Symlink flipping before sync is essential; otherwise a stale active link can cause a mode-specific file to be overwritten.

## Variant selection and synchronization flow

```text
tokens.json
  -> generate-palette-tokens.py -> palette_tokens.py
  -> load_variants()
  -> adaptive_palette() for active runtime only
  -> pure renderers
       -> sync_active_targets() (external active files)
       -> sync_repo_snippets() (tracked Light/Dark variants)
  -> write_if_changed()
  -> apply/reload helpers
```

Repository variants must use non-adaptive canonical palettes so they are deterministic and reviewable. Runtime wallpaper adaptation must not rewrite tracked Light/Dark artifacts. Explicit and automatic scheduling must call the same mode-application boundary. The current engine registry is explicit for Dark/Light and has special handling for Hyprland, Waybar, Rofi, Neovim, Kitty UI, OpenCode, and other non-uniform outputs.

Herdr is currently called from generic sync through `update_herdr_config`, while the Herdr design explicitly requires removing live active-file mutation from generic sync and assigning activation to a fail-closed service/helper. This is a direct conflict requiring consolidation before implementation.

## Acceptance evidence required

- **Rendering:** deterministic Light/Dark output for every declared target; stable ordering, LF endings, one trailing newline, and no unsupported fields.
- **Installation:** fresh install, repair, missing target, repository-managed target, external symlink, external regular file, and conflict classification with no destructive adoption.
- **Readability:** token/state matrix checks for text, muted text, selection, focus, borders where material, and semantic statuses across modes.
- **WCAG/APCA:** WCAG 4.5:1 minimum text policy and existing mode-aware APCA body thresholds; diagnostics identify mode, role, target, metric, and threshold. APCA advisories must not silently weaken WCAG.
- **Token parity:** exact canonical-to-`palette_tokens.py` synchronization, schema validation, required mode/role coverage, and no target-specific color literals.
- **Idempotency:** repeated generation and repeated apply produce no content or selector churn; `write_if_changed` reports unchanged outputs.
- **Rollback:** failed validation, installation conflict, reload failure, or partial activation restores selector/files/runtime where applicable and reports rollback failure distinctly.
- **Runtime/application:** explicit Light↔Dark switching and scheduled selection converge; ML4W hooks remain intact; Ghostty validates against the version-tied baseline; Herdr is skipped or fails closed when unsupported.
- **Scope evidence:** every result is tied to an explicit manifest and excludes the pre-existing dirty workspace.

## Proposed reviewable implementation slices

Keep each slice below 400 authored lines when feasible and do not mix ownership domains:

1. **Contract and inventory foundation:** finalize target manifest, token/generated parity, design-system matrix, WCAG/APCA diagnostics, and health discovery boundaries.
2. **Deterministic repository generation:** normalize Light/Dark variant registration and generated-artifact ownership for terminal, shell, editor/CLI, and ML4W snippets; retain special renderer boundaries.
3. **ML4W/Gentleman apply correctness:** reconcile symlink ordering, manual Tmux literals, hook imports, active reload behavior, installer target inventory, idempotency, and truthful aggregate status.
4. **Ghostty repair:** execute only the proven version-tied base-config remediation and its narrow validation; do not combine with palette changes.
5. **Herdr contract and renderer:** only after 0.7.3 evidence is complete; generate repository-owned variants without mutating live config from generic sync.
6. **Herdr installation/activation:** ownership classification, migration, atomic selection, reload observation, rollback, explicit/automatic convergence, and Fish compatibility.
7. **End-to-end evidence and operator docs:** rendering/readability checks, install/apply fixtures, rollback exercise, health/pytest evidence, and concise recovery documentation.

## Consolidation recommendation and risks

Adopt `repair-dreamcoder-theme-rollout` as the single parent change. Move the design-system contract into its prerequisite foundation, keep Ghostty as an isolated child slice, and keep Herdr as a gated later slice. Do not merge global Gentle AI repair into the implementation scope; retain only its evidence discipline and dirty-worktree boundary.

Primary risks are stale manual color duplication, incomplete health inventory, unsafe Herdr adoption, runtime reload failures being hidden, and contamination from the already-dirty worktree. The rollout should stop on unresolved runtime contracts, ownership ambiguity, failed parity/contrast gates, or any scope expansion beyond the declared manifest.

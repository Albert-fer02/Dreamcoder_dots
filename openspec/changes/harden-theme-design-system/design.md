# Technical Design: Harden Theme Design System

## Overview

This change adds a small, declarative contract around the existing theme engine rather than replacing its palette, renderers, or activation model. `DreamcoderThemes/dreamcoder/tokens.json` remains the only color authority. A reviewable design-system contract describes how canonical tokens become semantic roles, how the terminal-first targets map those roles, which state/contrast pairs are enforced, and which generated artifacts are owned.

Validation renders all three canonical modes in isolated memory, evaluates the contract, and compares only declared checked-in artifacts with deterministic expected bytes. The same command runs locally and in CI. No active user theme, home-directory state, wallpaper, screenshot, or all-renderer traversal participates in the gate.

## Repository Findings That Shape the Design

- The repository's canonical token path is `DreamcoderThemes/dreamcoder/tokens.json`, not the older `themes/dreamcoder/tokens.json` path referenced by some documentation and pre-commit patterns.
- `tokens.json` already contains `dark`, `light`, and `dusk`, while `tokens.schema.json` currently requires only `dark` and `light`.
- `scripts/generate-palette-tokens.py` generates `src/dreamcoder_theme/palette_tokens.py`, and the generated file already carries a source marker. Health validation does not currently compare generated bytes with canonical generation.
- `src/dreamcoder_theme/sync.py` uses a two-mode `D` registry for checked-in variants and accepts only `dark` or `light` as active runtime modes through `settings.theme_mode()`. This design does not expand runtime activation to dusk.
- `scripts/verify-theme-health.py` derives parity from keys present in dark/light, mixes policy, discovery, parsing, and reporting, and performs some environment-sensitive file inspection.
- The CI theme-health step is advisory because `.github/workflows/theme-validation.yml` sets `continue-on-error: true`.
- The current OpenCode repository check scans `DreamcoderOpenCode/.config/opencode/*.json` and requires that directory to contain only `dreamcoder.json`. Repository evidence shows that directory owns `opencode.json`, an application configuration file, while the checked-in generated theme is `.opencode/themes/dreamcoder.json` and runtime generation targets `<XDG_CONFIG_HOME>/opencode/themes/dreamcoder.json`. This is the primary root-cause candidate and must still be confirmed by the reproduction procedure below.

## Goals and Boundaries

### In scope

- Traceability from canonical token paths to semantic roles and terminal/component states.
- Explicit `dark`/`light`/`dusk` parity for a frozen terminal-first inventory.
- A machine-readable, reviewable state/contrast matrix.
- Canonical/static synchronization and declared generated-artifact integrity.
- Deterministic local and blocking CI validation.
- Root-cause correction and regression coverage for OpenCode artifact classification.

### Out of scope

- Palette redesign, broad token renaming, or renderer normalization.
- Enabling dusk as a selectable runtime mode.
- Requiring checked-in dusk siblings where the existing runtime lifecycle does not consume them.
- Validation of all 28+ renderers.
- Screenshot baselines or all-target visual regression.
- Changes to active user files during validation.

## Architecture

### 1. Declarative contract

Add `DreamcoderThemes/dreamcoder/design-system.json` as author-owned policy metadata. It contains no independently authored color values. All color references use canonical JSON paths such as `modes.{mode}.text` or deterministic derivation identifiers implemented by an existing renderer.

The contract has five sections:

```json
{
  "schema_version": 1,
  "modes": ["dark", "light", "dusk"],
  "roles": {},
  "targets": {},
  "matrix": [],
  "artifacts": []
}
```

- `roles`: role ID, layer (`primitive`, `semantic`, or `component-state`), canonical source path, optional parent role, and derivation/mapping rule.
- `targets`: target ID, renderer callable, required roles/states, explicit target-field mappings, unsupported-role mappings, and mode coverage.
- `matrix`: stable row ID, foreground role, background role, modes, target scope, metric, threshold source, and severity.
- `artifacts`: stable artifact ID, owner, lifecycle, source, generator, path, mode policy, discovery root, and validation method.

Add `DreamcoderThemes/dreamcoder/design-system.schema.json` so malformed policy fails before evaluation. Extend `tokens.schema.json` only to require all three modes and the existing enforced canonical roles; do not move target policy into the token schema.

### 2. Contract evaluator

Add `src/dreamcoder_theme/design_system.py` as a pure library. It loads canonical tokens and the declarative contract, resolves layered roles, invokes only the declared terminal-first renderer adapters, evaluates parity and matrix rows, and returns structured findings. It performs no writes and reads no user-home state.

Core internal contracts:

```python
@dataclass(frozen=True)
class Finding:
    code: str
    severity: Literal["error", "warning", "info"]
    mode: str | None
    target: str | None
    role: str | None
    artifact: str | None
    measured: float | str | None
    required: float | str | None
    message: str

@dataclass(frozen=True)
class RenderedTarget:
    target: str
    mode: str
    fields: Mapping[str, str]
    content: str
```

Target adapters normalize renderer output into semantic fields without changing renderer output. For example, OpenCode `theme.textSelected` maps to component role `selected.text`, and Kitty `selection_foreground` maps to the same role. A target format that cannot represent a role must declare a reviewed mapping such as `focus.border -> accent`; an absent field without such a mapping is an error.

Finding order is stable: `(code, target, mode, role, artifact)`. Messages contain stable identifiers and never include temporary paths.

### 3. Terminal-first inventory and parity contract

Freeze the enforced inventory to these existing consumers:

| Target   | Category                      | Renderer                                                         | Required contract                                                                                                          |
| -------- | ----------------------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Kitty    | terminal                      | `kitty_content` plus `kitty_ui_content` where UI state is needed | background, normal/muted text where representable, ANSI/status colors, selection, cursor/focus, significant border mapping |
| Ghostty  | terminal                      | `ghostty_content`                                                | background, text, ANSI/status colors, selection, cursor/focus mapping                                                      |
| Warp     | terminal                      | `warp_content`                                                   | background/surface, text, ANSI/status colors, accent/focus mapping                                                         |
| Starship | terminal-adjacent prompt      | `starship_content`                                               | prompt surfaces, normal/muted text, accent, status roles                                                                   |
| tmux     | terminal-adjacent multiplexer | `tmux_content`                                                   | status surface/text, active/inactive border, focus/accent, status roles                                                    |
| OpenCode | terminal-adjacent TUI         | `opencode_content`                                               | surfaces, normal/muted/selected text, focus/borders, semantic statuses, syntax mappings                                    |

Parity is evaluated from the required contract, not from whichever keys happen to exist. For every inventory target, the validator renders canonical `dark`, `light`, and `dusk` candidates in memory and requires the same required semantic role/state set. Equivalent mappings are required; equal color values are not.

Checked-in artifact inventory remains independent from semantic parity. Existing dark/light files may remain the only installed or checked-in variants where that is the established lifecycle. Dusk support is proven through deterministic renderer output and contract evaluation; this slice does not add dusk activation or unused files. If a declared checked-in artifact claims per-mode coverage, however, all modes it claims must exist and match exactly.

### 4. Layered token traceability

The evaluator resolves each field through this chain:

```text
DreamcoderThemes/dreamcoder/tokens.json
  -> canonical path for mode
  -> semantic role or documented derivation
  -> component/state role
  -> target adapter field
  -> optional declared artifact
```

Direct mappings record the canonical path. Derived renderer values record a stable derivation ID, input roles, and the owning renderer function, for example `mix(status.error, surface.background, 0.35)` owned by `renderers_opencode.py`. The contract must reject derivations that reference undeclared inputs.

`src/dreamcoder_theme/palette_tokens.py` remains a generated runtime representation. Refactor the existing generator into pure load/enrich/render functions and add a `--check` mode. `--check` compares exact expected bytes with `palette_tokens.py`, reports `GENERATED_DRIFT` with canonical source and regeneration command, and writes nothing. Generated headers contain source path, generator path, and contract version, but no timestamp or machine-specific value.

### 5. Enforceable state and contrast matrix

The following rows are the minimum blocking matrix. Threshold values are referenced from `tokens.json.guardrails`, not duplicated as independent constants in the policy file.

| State                           | Foreground / background roles             | Governing metric | Required policy                                                                                             | Severity                                                        |
| ------------------------------- | ----------------------------------------- | ---------------- | ----------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| Normal text                     | `text` / `bg`                             | WCAG             | `minimum_text_contrast` (4.5); `preferred_main_text_contrast` (7.0) remains an enforced main-text invariant | error                                                           |
| Body text APCA                  | `text` / `bg`                             | APCA             | 75 for light/dusk; `minimum_apca_body_dark` (50) for dark                                                   | error                                                           |
| Muted text                      | `muted` / `bg`                            | WCAG             | 4.5                                                                                                         | error                                                           |
| Muted observation               | `muted` / `bg`                            | APCA             | `minimum_apca_quiet`; does not replace the WCAG gate                                                        | warning unless the contract marks the target usage as body text |
| Selected text                   | `selection_fg` / `selection_bg`           | WCAG             | `minimum_terminal_selection_contrast` (7.0)                                                                 | error                                                           |
| Cursor/focus indicator          | `focus` or declared cursor role / `bg`    | WCAG non-text    | at least 3.0; terminal cursor keeps `minimum_terminal_cursor_contrast` (4.5)                                | error                                                           |
| Focus text                      | `on_focus` / `focus`                      | WCAG             | 4.5 when the target renders text on the focus color                                                         | error                                                           |
| Significant border              | `border_ui` / `bg` and `border_hi` / `bg` | WCAG non-text    | 3.0                                                                                                         | error                                                           |
| Error/warning/success/info text | status role / target surface              | WCAG             | 4.5                                                                                                         | error                                                           |
| Status body text                | declared status role / target surface     | APCA             | 75 for light/dusk, 50 for dark when rendered as body text                                                   | error                                                           |
| Accent text                     | `on_accent` / `accent`                    | WCAG and APCA    | WCAG 4.5 and existing `minimum_apca_on_accent`                                                              | error                                                           |

Non-text surface-difference checks may remain deterministic target integrity checks, but they must not be mislabeled as WCAG text contrast. Every failure includes matrix row ID, mode, canonical token/state pair, target, measured value, required value, metric, and artifact when applicable.

A current color that fails a newly explicit blocking row is not fixed by lowering the threshold. The implementation first verifies whether the target uses the value as body text, non-text decoration, or an incorrect mapping. Only a confirmed body-text failure permits a narrow canonical token or mapping correction, documented with before/after values for the affected target.

### 6. Generated artifact ownership and provenance

Artifact discovery is allowlist-rooted and contract-driven. The validator never recursively classifies arbitrary repository JSON as theme output.

Each artifact declaration includes:

- `owner`: renderer module or generator script;
- `source`: canonical token file and contract version;
- `lifecycle`: `checked-in`, `ephemeral`, or `workflow-specific`;
- `generator`: importable callable or script command;
- `mode_policy`: fixed mode, per-mode template, or active-mode runtime;
- `path` or `path_template`;
- `discovery_root` and file pattern;
- `validation`: exact bytes, normalized structured content, or schema/field validation.

Unexpected files fail only when they match a generated-theme pattern inside a declared discovery root. The diagnostic distinguishes `UNOWNED_ARTIFACT`, `STALE_ARTIFACT`, `MALFORMED_ARTIFACT`, `MODE_INCOMPLETE`, and `WRONG_SCOPE`. Application configuration files outside a declared theme root are not generated-theme candidates.

Checked-in outputs use exact deterministic comparison whenever the renderer controls complete file content. Runtime/ephemeral outputs are validated by rendering to a temporary directory in tests, never by inspecting `$HOME` in the health gate.

### 7. OpenCode lifecycle and exact resolution path

OpenCode is classified as `workflow-specific`:

- Canonical source: `DreamcoderThemes/dreamcoder/tokens.json`.
- Owner/generator: `src/dreamcoder_theme/renderers_opencode.py::opencode_content` orchestrated by `sync.py`.
- Checked-in repository default: `.opencode/themes/dreamcoder.json`, generated deterministically from the declared default mode (`light`) with `transparent_background=True`.
- Runtime artifact: `<XDG_CONFIG_HOME>/opencode/themes/dreamcoder.json`, ephemeral and generated from the selected active mode with `transparent_background=True`.
- Selector/config: `<XDG_CONFIG_HOME>/opencode/tui.json`, managed configuration, not a generated theme artifact.
- `DreamcoderOpenCode/.config/opencode/opencode.json`: application/agent configuration, explicitly outside theme-artifact discovery.
- Mode parity: `opencode_content` must render valid, equivalent contract fields for dark/light/dusk in memory even though the checked-in default has one fixed mode.

Implementation must follow this investigation sequence before changing classification:

1. From a clean checkout, run `PYTHONPATH=src python scripts/verify-theme-health.py` and capture the exact OpenCode finding and discovered names.
2. Confirm the validator constant and glob root, then classify every discovered JSON by consumer and writer. Do not move or delete files during diagnosis.
3. Trace generation from `settings.theme_paths().opencode` and `sync_active_targets()` to `opencode_content(..., transparent_background=True)`, then separately trace `sync_repo_snippets()` to `.opencode/themes/dreamcoder.json`.
4. Render dark/light/dusk OpenCode candidates into an isolated temporary directory and verify JSON shape, required target fields, mappings, and matrix rows.
5. Compare the checked-in `.opencode/themes/dreamcoder.json` with the exact expected default-mode bytes. Record whether any content drift exists independently from the discovery bug.
6. Replace `check_opencode_repo()`'s config-directory scan with the declared artifact contract rooted at `.opencode/themes`. Exclude `DreamcoderOpenCode/.config/opencode/opencode.json` by ownership, not by filename exception.
7. If step 5 finds drift, regenerate through the supported renderer workflow; do not hand-edit the artifact. If no drift exists, change only classification/discovery and tests.
8. Add positive coverage for valid default and all three in-memory modes, plus negative cases for malformed JSON, stale bytes, missing required mode role, and an unexpected JSON file inside `.opencode/themes`. Prove that `opencode.json` in its configuration directory is not discovered.

A different lifecycle may be adopted only if steps 2–5 produce contrary repository evidence. Such a change must update the contract and tests together; a global allowlist or weakened integrity check is prohibited.

## Deterministic Validation Pipeline

`PYTHONPATH=src python scripts/verify-theme-health.py` remains the single public command and executes these phases in order:

1. Validate `tokens.json`, `tokens.schema.json`, `design-system.json`, and its schema.
2. Require exactly the contract modes and canonical role coverage.
3. Run canonical-to-`palette_tokens.py` exact synchronization check.
4. Render only the six terminal-first targets for all three modes in memory with adaptive behavior disabled.
5. Validate target parity and explicit mappings.
6. Evaluate matrix rows.
7. Validate declared checked-in artifacts and scoped discovery roots.
8. Emit sorted findings and return nonzero if any `error` exists.

The command has no network access, no current-time input, no wallpaper adaptation, no active-mode environment dependency, and no home-directory reads. Tests may pass fixture roots explicitly. CI and local execution use the same default repository root and policy.

Update `.github/workflows/theme-validation.yml` to remove `continue-on-error` from theme health. Keep preview generation separate; preview drift does not substitute for contract health. Update `.pre-commit-config.yaml` path filters to the actual `DreamcoderThemes/dreamcoder/` path and include the contract, schemas, generator, terminal-first renderer modules, `palette_tokens.py`, and health validator.

## Test Strategy

### Unit tests

- Role resolution reports canonical path and derivation chain.
- Missing canonical role, unknown derivation input, or cyclic role mapping fails.
- Token schema rejects missing dusk.
- Each target adapter produces the same required semantic field set for dark/light/dusk.
- Explicit unsupported mappings pass; silent omissions fail.
- Every matrix row reports complete diagnostic context and uses its declared metric/threshold.
- `palette_tokens.py` exact match passes; one-byte drift fails with regeneration guidance.
- Finding ordering and exit status are stable across repeated runs and differing irrelevant environment variables.

### OpenCode regression tests

- Valid default checked-in content matches renderer output.
- Dark/light/dusk in-memory outputs satisfy required fields and state mappings.
- Corrupted JSON, stale content, missing selected text, and missing dusk contract coverage fail with distinct codes.
- An unexpected theme JSON inside `.opencode/themes` fails as unowned.
- `DreamcoderOpenCode/.config/opencode/opencode.json` is not scanned as a generated theme.
- Temporary runtime generation writes only inside the fixture root and validates successfully.

### Integration and CI tests

- Run `python -m pytest tests/ -v` and existing coverage gate.
- Run `PYTHONPATH=src python scripts/verify-theme-health.py` twice and assert equivalent findings/exit status.
- Verify the CI workflow has no advisory override on theme health.
- Verify pre-commit triggers on actual canonical, contract, renderer, generator, and validator paths.
- Review generated terminal-first diffs textually when a canonical color or mapping changes; screenshots are not required.

## Rollout and Migration

1. Land the schemas, declarative contract, evaluator, and focused tests without changing colors or activation behavior.
2. Run the OpenCode investigation and correct discovery/ownership first; regenerate only on proven drift.
3. Enable exact `palette_tokens.py` synchronization and terminal-first three-mode parity.
4. Address any real matrix failure by correcting classification or mapping before considering a minimal canonical color adjustment.
5. Make CI blocking only after the same local command passes from a clean checkout on supported Python versions.

The contract schema is versioned. Future inventory expansion requires an explicit contract edit and tests; it cannot occur through broad file discovery.

## Rollback

Revert the contract evaluator, health CLI changes, generated-output updates, and CI gate as one unit. Restore generated files through the previous supported generator, not manual edits. A temporary CI downgrade must be explicit and time-bounded. Preserve the OpenCode ownership diagnosis and regression evidence even if enforcement is rolled back.

## Risks and Mitigations

- **Dusk parity could accidentally become runtime activation scope.** Validate dusk in memory; do not change `theme_mode()` or runtime selectors in this slice.
- **A generic adapter layer could become an all-renderer framework.** Freeze adapters to the six targets and reject inventory expansion without a contract change.
- **New APCA rows may expose real visual failures.** Verify usage classification first, preserve existing thresholds, and allow only narrow documented corrections.
- **Exact artifact comparison can be noisy.** Require pure renderers, stable serialization, no timestamps, and repository-root-relative diagnostics.
- **OpenCode configuration could again be mistaken for a theme.** Scope discovery to `.opencode/themes` and distinguish selector/config ownership in the contract.
- **Generated token checks could mutate canonical input.** `--check` must be write-free; generation functions must return content before any explicit write.
- **CI may block unrelated changes due to stale hook paths or environment state.** Correct path filters and remove active machine state from validation before enabling the blocking gate.
